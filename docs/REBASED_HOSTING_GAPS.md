# Rebased Hosting 集成 Parity 差异盘点

对应 `docs/ROADMAP.md` P11 任务。与 P1（`docs/REBASED_ACTION_INVENTORY.md` 的"GitHub 插件"/"GitLab 插件"两节）配套，不重复已记录的能力点列表。P1 已经把 GitHub/GitLab 的全部能力点标记"P2，归入 P11/M13 决定"——这是一个笼统的占位决定，本文档的任务是把它具体化为可以逐项验收的处置清单，并验证"无账号时核心 Git 流程完整"这条当前就能检验的验收标准。本文档不代替用户做产品范围决策，只提供决策所需的技术事实和选项矩阵。

## 1. "无账号时核心 Git 流程完整"验收现状（含代码证据）

**结论：这条验收标准目前已经满足，有明确代码证据，不是推测。**

核查 `internal/repo/repo.go` 里全部远程相关函数：

- `RemoteWithPolicy`（`repo.go:364-420` 一带）：处理 fetch/pull/push 三种操作，内部是纯粹的参数拼接——`args = []string{"fetch", "--progress", "--prune"}`（`repo.go:368`）、`args = []string{"pull", "--progress"}`（`repo.go:373`）、`args = []string{"push", "--progress"}`（`repo.go:392`），后续拼接远程名/分支名后直接交给 `r.runner.Run` 执行系统 `git` 命令。**没有任何代码检查远程 URL 是否指向 github.com/gitlab.com 或其他特定域名**，也没有任何分支逻辑区分"这是 GitHub 仓库"和"这是任意 Git 服务器仓库"。
- `PlanPush`/`ExecutePush`（`repo.go:446-525`）、`PlanForcePush`/`ExecuteForcePush`（`repo.go:526-600`一带）：同样只操作 `plan.Remote`（远程名字符串）和 `plan.Branch`（分支名字符串），拼接成标准 `git push`/`git push --force-with-lease` 命令，不涉及任何平台 API 调用。
- 全局搜索 `internal/` 目录下 `password`/`credential`/`oauth`/`personal.access.token`/`api.github`/`api.gitlab` 等关键词：**零匹配**（见第2节详述）。

**技术判断**：当前所有远程操作（Clone 的后端能力虽然 P1 标记"未实现"，但规划方案本身也是纯 `git clone <url>`）完全基于用户提供的 remote URL 字符串和系统 git 的凭据机制工作，没有任何代码路径假设或依赖 GitHub/GitLab 账号的存在。这条验收标准对核心 Git 流程（克隆、Fetch、Pull、Push、Force Push、分支操作）而言，**现在就是满足的**，不需要等 P11 决策完成才能通过。P11 要决策的是"要不要加托管平台专有功能"，不影响这条验收标准已经成立的事实。

## 2. 凭据处理安全核查

**结论：代码里没有任何自己存储或管理凭据的逻辑，这是符合规格 §4.1/§7 要求的"正确的不做"，不是缺口，也不是需要标记的安全问题。**

规格 §4.1"凭据由系统 Git 凭据助手处理"、规格 §7"SSH/HTTPS 认证交由 Git credential helper/SSH agent，客户端不另存明文密码"。

核查方法：对 `internal/` 全目录（含子目录）精确搜索 `password`、`Password`、`credential`、`Credential`、`oauth`、`OAuth`、`personal.access.token`、`api.github`、`api.gitlab` 等关键词，**全部零匹配**。唯一会让人联想到"认证"的是 `gitexec` 包的子进程调用机制本身——但它只是把参数传给系统 `git` 二进制，不拦截、不读取、不存储任何认证材料；认证交互（弹出系统凭据提示、读取 SSH agent、走 credential helper）完全发生在 `git` 子进程内部，客户端进程看不到也不需要看到任何密码的实际内容。

**结论明确**：这不是"还没做"的缺口，是架构上正确的选择——客户端不应该、也没有尝试过自己处理认证。如果未来做 GitHub/GitLab API 集成（PR/MR 浏览等），那部分功能会引入新的认证需求（API token 或 OAuth），需要重新评估凭据存储方式，但那是第4节要讨论的全新范围，不影响当前核心 Git 流程的安全状态评估。

## 3. Git 协议原生能力 vs 平台专有 API 能力的边界

区分"看起来像 GitHub/GitLab 功能，但实际上 Git 协议本身就能做到"和"必须调用平台 REST/GraphQL API 才能做到"两类，帮助理解处置选项的技术基础：

| 能力 | 技术实现基础 | 说明 |
|---|---|---|
| 克隆 GitHub/GitLab 仓库 | **纯 Git 协议**，`git clone <url>` | 不需要任何平台 API，只要有仓库 URL（公开仓库）或有权限的凭据（私有仓库，走系统 credential helper），任何 Git 服务器都一样。P1 已标记 `Git.Clone` 是 P0 核心功能，这个能力和"GitHub/GitLab 专有"无关，是通用 Git 能力。 |
| Checkout PR/MR 对应的分支 | **纯 Git 协议**，前提是知道分支名或 ref | `git fetch origin pull/123/head:local-branch-name`（GitHub 的 PR ref 约定）或直接 `git fetch` 对应的源分支。核心 Git 能力（Fetch + Checkout，均已在 P1-P10 盘点范围内）已经能完成这个动作，**缺的只是"从哪里知道 PR 123 对应的 ref 是什么"这一条信息**——这条信息目前只能从 GitHub API 或网页界面获取，无法从 `git` 命令本身得到（PR/MR 是平台概念，不是 Git 对象）。 |
| 浏览"我的仓库列表"再选一个克隆 | **必须平台 API** | Git 协议本身没有"列出某用户在某平台上有哪些仓库"的概念，这个列表只存在于 GitHub/GitLab 的服务端数据库里，必须调用对应的 REST/GraphQL API 才能拿到。 |
| PR/MR 浏览（列表、筛选、timeline、评论） | **必须平台 API** | PR/MR 本身、评论、审查状态、标签等都是平台数据库里的记录，不是 Git 对象（Git 只知道 commit/branch/tag），没有平台 API 无法获取。 |
| PR/MR 创建 | **必须平台 API** | 创建 PR/MR 这个动作本身是平台概念上的"发起一次代码审查请求"，Git 协议里没有对应命令。 |
| PR/MR Review（Approve/Request Changes/评论） | **必须平台 API** | 同上，审查状态和评论存储在平台侧。 |
| 查看 PR/MR 的 Diff | **可以用纯 Git 协议近似实现**，但不完全等价 | 如果已经 fetch 了 PR 对应的分支，用现有核心 Diff 能力（P5 已盘点）比较"PR分支 vs 目标分支"可以看到代码差异，这和平台网页上展示的"PR Diff"在内容上基本等价，但缺少平台侧的"哪些是本次PR新增的评论定位"等附加信息。 |
| Gist 创建 | **必须平台 API** | 完全是 GitHub 平台概念，和 Git 协议无关。 |

**对决策的意义**：表格第2、3行（Checkout PR分支、PR Diff查看）说明即使不做任何平台 API 集成，核心 Git 能力加上"用户自己从网页复制一个分支名/ref 手动输入"这种笨拙但可行的路径，也能覆盖相当一部分实际需求，只是便利性和 Rebased 基线的"一键操作"有差距。表格其余行说明"浏览列表"、"PR/MR 管理本身"这些是无法绕过平台 API 的，要做就必须引入 API 集成和对应的认证机制（这会改变第2节的"零凭据代码"现状，需要新设计）。

## 4. 各能力点的处置选项矩阵（不代为决策）

对 P1 已登记的每个 GitHub/GitLab 能力点，给出三选一处置选项，每项说明代价和收益，不给结论性建议：

| 能力点 | 选项 (a) 不实现 | 选项 (b) 通用方式实现等价能力 | 选项 (c) 需要专门平台 API 集成 |
|---|---|---|---|
| GitHub/GitLab 账号登录 | 代价：无法支撑后续任何需要账号的功能。收益：零工作量，零新增攻击面（不存储/处理任何 token）。 | 不适用——登录本身就是账号相关动作，没有"不依赖平台的登录"这种中间形态。 | 需要 OAuth（走浏览器授权流程，需要应用在 GitHub/GitLab 注册 OAuth App，涉及 redirect URI、client secret 管理）或 Personal Access Token（用户手动生成并粘贴，实现更简单但用户体感是"自己管理密钥"）。代价：需要新的凭据存储机制（和第2节现状完全不同的新设计），需要考虑 token 的本地加密存储方案。收益：解锁下面所有依赖账号的能力。 |
| 浏览仓库列表再克隆 | 代价：用户必须自己去网页复制 URL 再粘贴到克隆框。收益：零工作量。 | 不适用——"列出我的仓库"必须调 API，没有不依赖 API 的等价方式。 | 需要先有选项(c)的账号登录，再调用 `GET /user/repos`（GitHub REST）或等价 GraphQL/GitLab API，工作量中等（一次性的列表拉取+搜索框，不涉及复杂状态管理）。 |
| Checkout PR/MR 分支到本地 | 代价：用户需要自己知道/查到 PR 对应的分支名或 ref，手动在现有分支/checkout 功能里输入。收益：零工作量，且核心 fetch+checkout 能力（P1-P10 已覆盖）已经能执行真正的 checkout 动作，只是没有"自动从 PR 列表跳转"这层便利。 | **部分可行**：如果已知 PR 编号，GitHub 有固定的 ref 约定 `refs/pull/<N>/head`，可以不调用 REST API，直接 `git fetch origin refs/pull/<N>/head:local-branch` 拿到对应代码（GitLab 有类似但不完全相同的 `refs/merge-requests/<N>/head` 约定）。这是"知道编号就能不经过账号登录完成 checkout"的中间路径，但用户仍需要从网页获取 PR/MR 编号，无法在客户端内"浏览列表后点击"。代价：需要为 GitHub 和 GitLab 分别处理不同的 ref 命名约定，但不需要账号/API。收益：免去账号体系，用最小改动覆盖"我知道PR号，想在本地看代码"的常见场景。 | 完整体验（从列表点击直达）需要选项(c)。 |
| PR/MR 浏览（列表/筛选/timeline） | 代价：完全无法在客户端内查看，用户需要去网页。收益：零工作量。 | 不适用，必须API。 | 需要账号登录（选项c第一行）+ 对应的列表/详情 API 调用，工作量较大（需要设计列表UI、筛选UI、详情展示，参照 P7 已分析的 Log 视图可能有布局模式可借鉴，但数据源和交互逻辑是全新的）。 |
| PR/MR 创建 | 同上，用户去网页创建。 | 不适用。 | 需要账号登录 + 创建 API，还需要让用户选择目标分支/源分支（这部分可以复用 P6 已盘点的分支选择 UI 模式），工作量中大。 |
| PR/MR Review（Diff+评论+Approve等） | 同上。 | **Diff 部分可行**（第3节已说明，fetch 后用现有 Diff 能力近似查看），评论/Approve 等审查动作必须 API。 | 评论/Approve/Request Changes 需要账号 + 写 API，工作量较大，且涉及实时性（别人的评论什么时候同步）等体验设计问题。 |
| Gist 创建 | 代价：无。收益：零工作量，且这是离"Git客户端"定位最远的一项（Gist本质是独立代码片段分享服务，不是仓库操作）。 | 不适用。 | 需要账号 + Gist API，工作量小但产品定位上最值得质疑是否需要（规格通篇围绕"仓库"工作流，Gist不操作仓库）。 |

## 汇总：P11 待办清单与决策请求

**不需要决策、现在就可以确认的结论**
1. "无账号时核心 Git 流程完整"验收标准**已经满足**（第1节代码证据），P11 决策结果不会影响这条标准的通过状态，可以在 ROADMAP 里标记这一条验收子项为已通过。
2. 当前凭据处理方式（完全不自己存储，交给系统 git）**符合规格要求，不是缺口**，只要不引入第4节选项(c)类的功能，这个安全状态会一直保持。

**需要用户决策的核心问题（决定整个 P11/M13 范围）**
3. 是否要引入 GitHub/GitLab 账号体系？这是所有后续能力的前提闸门——如果答案是"不"，第4节表格里标选项(a)的行全部确定，文档可以直接归档为"决策完成：不做托管平台集成"；如果答案是"是"，需要进一步决定走 OAuth 还是 Personal Access Token（影响凭据存储设计，是否需要新的安全评审）。
4. 如果暂时不想做完整账号体系，是否采用第4节"Checkout PR分支"选项(b)的中间路径（利用GitHub/GitLab固定的ref命名约定，不登录也能fetch PR对应代码）？这是一个工作量很小、不引入新凭据逻辑、但能覆盖常见场景的折中选项，值得单独决策（不必和"要不要做完整账号体系"绑定在一起）。
5. Gist 创建这一项，建议无论账号体系决策如何，都优先确认是否纳入范围——它离"Git 仓库客户端"的产品定位最远，即使做了账号体系，也可以单独排除。

**依赖决策结果才能排期的后续工作（本文档不展开设计，待决策后再细化）**
6. 若决定引入账号体系：需要新设计凭据存储机制（这会是继 P3`internal/settings`、P8仓库操作状态检测、P9会话级stash状态之后的第四类需要新持久化/状态管理能力的基础设施，但性质不同——涉及敏感凭据，需要比普通设置更谨慎的存储方案，可能需要操作系统级的凭据库集成而不是简单的 JSON 文件）。
7. 若决定做选项(b)的"知道PR号即可fetch"折中路径：工作量小，可以独立于账号体系决策先做，是本文档里唯一一个"技术上确定、不需要等待决策"的实现项（但是否要做，仍然是一个范围决策，不是技术必选项）。
