# Rebased 设置与动作系统 Parity 差异盘点

对应 `docs/ROADMAP.md` P10 任务。与 P1（`docs/REBASED_ACTION_INVENTORY.md`）、P2（`docs/REBASED_UI_PARITY_GAPS.md`）、P3（`docs/REBASED_SPLITTER_PERSISTENCE_GAPS.md`）、P4（`docs/REBASED_COMMIT_SHELF_GAPS.md`）、P5（`docs/REBASED_CHANGES_DIFF_GAPS.md`）、P6（`docs/REBASED_BRANCH_REFS_GAPS.md`）、P7（`docs/REBASED_LOG_GAPS.md`）、P8（`docs/REBASED_HISTORY_CONFLICT_GAPS.md`）、P9（`docs/REBASED_STASH_GAPS.md`）配套，不重复已记录内容。本篇重点评估"动作系统"和"设置持久化"两大基础设施本身，不是盘点某个具体 Git 操作功能。

## 1. Keymap 包现状解剖

**结论：`internal/keymap/actions.go` 目前只是一个 6 项的导航枚举，和 `docs/UI.md` §5 设计的"动作注册表"概念相比，缺少几乎全部设计字段，且没有任何按键映射或冲突检测的代码雏形。**

全文（`actions.go:1-28`）：

```go
type ActionID uint8

const (
    ShowChanges ActionID = iota
    ShowLog
    ShowBranches
    ShowStash
    ShowTags
    ShowRepositories
)

type Action struct {
    ID   ActionID
    Name i18n.Key
}

var Actions = [...]Action{...}
```

对照 `docs/UI.md` §5"动作注册表：每个动作是一个常量 `ActionID`，带 i18n 名称、适用上下文、是否需要选中项"——当前 `Action` 结构体**只有 `ID` 和 `Name` 两个字段**，缺：
- **适用上下文**（`Global`/`Changes`/`Log`/`Diff`/`Conflict`/`TextInput`/`Dialog`，UI.md §5 已列出枚举值）——完全没有对应字段或类型。
- **是否需要选中项**——完全没有对应字段，意味着即使有了动作注册表，也无法表达"Stage 这个动作只在有未暂存文件被选中时才可执行"这类前提条件，当前这类判断全部散落在 `shell.go` 各个 `Disabled(...)` 调用里（P4 已经引用过 `commitID` 按钮的 `Disabled` 条件），是硬编码在绘制代码里，不是从动作定义读出来的。

全局搜索调用点：
- `keymap.` 被 `shell.go`、`shell_test.go`、`changes_test.go` 引用，确认全部用途是读取 `keymap.ShowXXX` 常量做导航路由判断（`m.Active == keymap.ShowLog` 这类），**没有发现任何"按键 → ActionID"的映射表**，没有发现 `map[KeyCombo]ActionID` 或类似结构，哪怕是空的占位声明都不存在。
- `app.Config.OnShortcut`：全局搜索零匹配，**从未被调用**。
- `app.Config.OnKey`：**调用了一次**（`shell.go:485`），但不是通过动作系统——是一个硬编码的 `switch`/`if` 链，直接处理分栏键盘导航（`SplitterState.Key`）、文本输入框的光标移动（`m.message.move`）、Log 表格的方向键选择（`m.logTable.Key`）。这是**按控件直接处理按键**，不是"按键 → 查动作注册表 → 执行动作"的间接层。换句话说，Viva 提供的两个接入点，一个完全没用过（`OnShortcut`），另一个用了但绕过了动作系统直接写死逻辑（`OnKey`）。

**技术判断**：现有的 `ActionID`/`Action` 类型定义可以保留作为起点（命名空间延续没问题），但结构体本身需要重新设计（加字段），且目前完全没有"消费"这套注册表来实际绑定按键的机制——`OnKey` 里的硬编码逻辑将来如果要改造成"从动作注册表读取"，需要重写这部分调用点，不是简单扩展。

## 2. 动作数量级估计与命名空间影响

**估计数量级：全部规划中的 Git 操作动作化后，总数在百位量级（约100-150个），不是十位数，这对 ActionID 的命名空间设计和分类方式有直接影响。**

估算依据：
- `docs/REBASED_ACTION_INVENTORY.md`（P1）逐项登记的 git4idea 动作约115个顶层条目，减去 P1 已标记"不属于本项目范围"的 IDE 平台能力（VFS、统计采集、Search Everywhere 框架等，约10余项）和明确排除/延后的产品决策项（独立Staging Area模式、模态提交、GitHub/GitLab 账号集成等，约15-20项），落在"本项目需要做"范围内的仍有约80-90项。
- 加上 P4-P9 过程中在"已有雏形但发现具体缺口"时新确认需要动作化、但未必和 git4idea 动作一一对应的操作：Amend 开关（P4）、分组级批量 Stage/Unstage（P5）、Reset 三模式 soft/mixed/hard（P8）、Merge/Rebase/CherryPick/Revert 各自的 Continue/Skip/Abort（P8，约10个独立动作）、Stash 的 Save/Apply/Pop/Drop/Clear/Branch（P9，6个）、Copy SHA/复制路径/复制提交消息（P2/P5/P7，3个零散的复制类动作）。
- 这些加总后，**百位量级**是合理估计，不是十位数——这意味着 ActionID 不能停留在当前"一个扁平 `const` 块里塞6个值"的设计方式，需要考虑分类命名（比如按 `Changes.*`/`Log.*`/`Branch.*`/`Stash.*` 做前缀分组，或者用字符串常量而非连续的 `uint8` 枚举，避免插入新动作时产生枚举值位移的兼容性问题——当前 `ActionID uint8` 用 `iota` 连续赋值，如果后续按字母或逻辑顺序插入新动作而不是永远追加到末尾，会导致已持久化的用户快捷键配置（一旦有了P3的持久化层）里存的数字值错位）。

**对 P3 持久化设计的直接影响**：如果 P3 的 `settings.json` 要存储用户自定义的键位映射，这个映射的键不能是 `ActionID uint8` 的裸数值（枚举值在代码里重排后数值会变化，导致存量用户配置失效），应该用一个**稳定的字符串标识符**（比如 `"changes.stage"`、`"log.cherry_pick"`）做序列化键，`ActionID` 内部仍可以是高效的整数类型用于运行时查表，但持久化层需要字符串映射这一层转换。这是本次核查发现的一个此前文档没有提到的具体设计约束。

## 3. 设置项全景（已有运行时字段/全新项分类）

**结论：规格 §6 要求的设置项可以分成三类——"已有运行时字段只差持久化"、"后端能力和运行时字段都没有，需要新建"、"纯界面层新建"，三类都依赖 P3 的 `internal/settings` 包先存在，但第一类在逻辑实现上的增量成本最低。**

| 设置项（规格 §6 原文对应） | 当前状态 | 分类 |
|---|---|---|
| Git 可执行文件路径/自动检测/版本 | 已有检测逻辑（`internal/git` 的版本探测，M0 已完成），但没有"设置界面里手动指定路径"的交互和持久化 | 已有运行时能力，缺持久化+UI |
| Git identity（user.name/user.email及来源） | **完全不存在**（P4 已确认后端零实现，不是UI缺失） | 全新项，两端都要做 |
| 默认远端/Push行为/Pull策略 | Pull 策略已有运行时选择（`m.pullPolicy` 一类字段，P4 已引用"仅保留在当前窗口会话中"），远端选择已有运行时字段（P6 已分析的 `m.selectedRemote`） | 已有运行时字段，缺持久化 |
| Fetch pruning/子模块递归等 | 全局搜索未发现相关字段或git命令参数（本次核查未发现任何 `--prune`/`--recurse-submodules` 的使用），**完全不存在** | 全新项，两端都要做 |
| SSH/HTTPS认证 | 规格明确要求"交由Git credential helper/SSH agent，客户端不另存明文密码"——即这条本身不需要客户端做任何存储，只需要不做任何拦截，当前代码没有发现任何凭据拦截逻辑，**符合规格要求的"不做"状态**，不算缺口 | 不适用（按规格就不应该做） |
| 环境变量/额外参数（高级设置） | **完全不存在** | 全新项 |
| Keymap预设与自定义 | 依赖本文档第1、2节的动作注册表先建立，当前0个可绑定的操作级动作，这条排第二优先级之后 | 全新项，依赖地基 |
| Diff并排/上下方向 | 上下排列本身是已知的Viva框架限制（`docs/UI.md` §8，不是本节新发现），并排是默认且唯一支持的方向，没有"选项"的意义（只有一种选择） | 不适用于当前阶段（框架限制） |
| 文件列表扁平/树状 | 已有运行时字段（P5已分析的`m.treeMode`），只是没有持久化（P3已指出） | 已有运行时字段，缺持久化 |
| Log默认范围和列可见性 | 列可见性当前固定（P7已分析的5列定义是硬编码数组，不是用户可配置），默认范围（`--all` vs 当前分支）是硬编码行为（P7已指出`logRef`为空时固定`--all`），**都不存在"可配置"这层** | 全新项（配置能力本身不存在，不只是缺持久化） |
| 主题/字体/高对比 | 规格要求"使用Viva和目标平台能力实现"，全局搜索未发现任何主题切换或高对比读取逻辑，**完全不存在** | 全新项，依赖Viva提供系统高对比状态查询能力（这部分可能也要先确认Viva是否已提供这个API，类似P8发现的"没人问过Viva是否支持拖拽"这类情况，本次未深入核实Viva侧能力，标记为待确认） |

**汇总**：设置项全景里，"已有运行时字段只差持久化"这一类（Pull策略、远端选择、文件列表模式、三个SplitterState——P3已提）是成本最低的一批，一旦 `internal/settings` 包建好，这批可以快速接上；"全新项"（Identity、Fetch pruning、环境变量、Log范围/列配置、主题高对比）需要先有后端能力或配置模型本身，工作量更大。

## 4. Find Action 命令面板的前提依赖

**结论：代码里零实现，且这个功能本质上是"动作注册表的UI呈现层"，不是独立功能——当前动作注册表只有6个导航项，即使现在就实现命令面板本身的UI组件，搜索结果也只能是这6个导航目标，不会有实际产品价值。**

全局搜索 `components.Command`、`Command(`、"Find Action"、"命令面板"相关字符串：零匹配，没有发现任何调用或占位代码。

依赖关系很直接：命令面板的核心交互是"输入关键词 → 模糊匹配动作名称 → 执行选中的动作"，如果可执行的"动作"集合只有 ShowChanges/ShowLog/ShowBranches/ShowStash/ShowTags/ShowRepositories 这6个视图切换，命令面板相当于一个只能做视图跳转的搜索框，和真正的 Find Action（能呼出"Commit"、"Create Branch"、"Cherry-pick"等上百个操作）体验上有本质差距。**技术判断：命令面板不应该作为独立任务提前实现，它的实现时机应该跟在"动作注册表扩充到覆盖主要Git操作"之后**，否则做出来的东西在当前阶段验证不出真实价值，也可能在动作注册表重新设计（第1、2节已指出的字段扩充、命名空间调整）后面临重写。

## 5. 命令日志与脱敏诊断

**结论：当前完全没有任何形式的命令执行历史记录，但扩展点非常明确——所有 Git 命令都唯一地经过 `gitexec.Runner.Run`，这是一个天然的、未被使用的记录接入点。**

读取 `internal/gitexec/exec.go` 全文：`Runner.Run(ctx, command Command) (Result, error)` 是整个项目调用系统 `git` 的唯一入口（符合 AGENTS.md"只通过子进程调用系统git"的约束），每次调用都拿到完整的 `command.Args`（执行的参数）、`Result{Stdout, Stderr, ExitCode}`。**但函数内部没有任何地方把这次调用的记录写入一个切片、环形缓冲区或文件**——执行完就返回，调用方（`internal/repo`）拿到结果后也没有发现任何"记录最近N次命令"的逻辑（本次搜索 `internal/repo/repo.go` 未发现任何类似 `recentCommands`/`commandLog` 的字段）。

规格 §6"操作日志：展示最近执行的Git命令、退出状态和错误输出"和 §7"不把Git stderr中可能含凭据的内容写入普通日志；诊断导出前允许检查内容并遮蔽认证信息"要求的功能，当前**后端数据源和UI展示都是零**，不是"UI没画出来"的问题。

**技术判断**：最自然的实现位置是在 `Runner.Run` 这个单一入口点加一个可选的记录回调（类似现有的 `OnProgress func(string)` 字段设计模式，`exec.go:24`已经有这种"侧路通知"的先例），记录内容应该在这一层就做好 stderr 的敏感信息识别（比如匹配URL里的`user:password@`模式、识别常见认证头），而不是在UI层做字符串替换——数据源头部脱敏比展示层脱敏更安全（避免未脱敏的原始数据在内存里停留更久或被其他地方意外读取）。这是本次核查给出的一个具体实现建议，不只是指出缺口。

**命令日志的另一层考虑**：规格要求的是"最近执行的"命令，暗示这是一个有限大小的环形缓冲区（不需要无限持久化所有历史命令），这个记录本身可以是纯内存的会话级状态（不强制要求存入 P3 的持久化层），但如果要支持"诊断导出"（规格提到的导出功能），导出时的脱敏逻辑需要和记录时的脱敏逻辑一致，建议脱敏在写入记录的那一刻就完成，导出只是读取已经脱敏过的记录，不是在导出时再做一次独立的脱敏处理（降低"两处脱敏逻辑不一致导致遗漏"的风险）。

## 6. i18n 遗漏的系统性检查

**结论：抽样检查显示 `graph.go` 的硬编码前缀（P2已发现）目前看起来是孤例，不是系统性问题——`shell.go`（1878行，全项目最大的UI文件）里几乎所有用户可见文案都正确走了 `i18n.Text`，只有一处非文案性质的例外。**

检查方法：在 `internal/ui/shell/*.go`（排除测试文件）里搜索看起来像用户可见文案但没有经过 `i18n.` 调用的字符串字面量模式（`f.Text("大写字母开头的词"`、`Title: "..."`、`Placeholder("..."`等）。

结果：`shell.go:849` 唯一命中 `f.Text("R").Color(...)`——这是顶部工具栏 logo 的替代文字（P2已分析过，用文字"R"模拟矢量图标），**不是需要翻译的用户可见文案**，是品牌标识的占位符号，不算i18n遗漏。

除此之外没有发现其他硬编码英文文案混入 `shell.go`。对照 `graph.go` 第2、3节已确认的 `"HEAD"`/`"tag: "`/`"remote: "`/`"branch: "` 四处硬编码——`graph.go` 是一个相对独立的小文件（commit graph 和 ref label 绘制逻辑），这四处硬编码很可能是因为这个文件在开发时被当作"纯粹的图形计算工具函数"而没有像 `shell.go` 主绘制流程一样被要求过一遍i18n检查清单，是局部疏漏而非项目普遍存在未经i18n检查的开发习惯。**本次核查没有发现"这类遗漏不是孤例"的进一步证据，倾向于反证：这是一个孤立的点，但建议在后续新增代码（尤其是独立的小工具文件）时，把i18n检查作为代码审查的标准项，防止类似疏漏再次出现在新文件里。**

## 7. 工作量分级（地基优先）

**地基（必须最先做，决定后续设计起点，不是和其他功能并行的一项）**

2. **决定动作注册表的覆盖范围边界**：参考第2节的百位量级估计，建议先完整列出 P1-P9 已经发现需要动作化的全部操作（不需要本文档重新列举，P1-P9各篇已经逐项提及），一次性设计好分类命名空间，而不是边做功能边随手加 ActionID（后者会导致命名风格不统一、后续批量迁移成本高）。
